### 7.1 问题 1：「悬崖一样的切割线」（频谱紫色垂直线 + 听觉 click）

**用户描述**：截图上波形里有「悬崖」般的不连续，频谱图上对应一条紫色窄带（所有频率同时被激发）。第二张截图是「正常应该这样」——平滑衰减。

**直接根因**：`src-tauri/src/lib.rs::gate_segment_head_tail` (lib.rs:7395-7514)
- 该函数把头尾 below-threshold 的 sample 逐字节置零
- **置零位置和首个非零样本之间是阶跃跳变** → click 噪声
- 代码片段：
  ```rust
  // lib.rs:7498-7511
  let head_bytes = head * frame_size;
  if head_bytes > 0 {
      for b in &mut bytes[data_start..data_start + head_bytes] {
          *b = 0;  // ← 一刀切到 0，没有 ramp
      }
  }
  ```

**间接根因**：`write_pcm_wav_segment` (lib.rs:7671) 也是 ffmpeg `-ss / -t` 硬切，**没有 fade in / fade out**。

**整改方案 M1（高优先级）**：
- **A（推荐，最小改动）**：在 `gate_segment_head_tail` 置零边界加 **3-5ms 线性 ramp**（head 从 0 渐升到原样本，tail 从原样本渐降到 0）。code 位置 lib.rs:7498-7511，加一个 ramp_frames = sample_rate * 5 / 1000 的过渡区间。
- **B（更干净）**：彻底删 `gate_segment_head_tail`，把 fade 直接合入 `trim_segment_head_tail` 输出。
- **测试**：合成一段头部 -20dB 噪声 + 中段 -3dB 信号的 WAV，gate 后用 FFT 验证没有不该有的全频段噪声。

### 7.2 问题 2：「前面几乎没有静音段了」

**用户描述**：截图 3 显示一段音频开头几乎没有 silence padding，立刻进入声音。

**根因链**：
1. `pre_roll_ms` 默认 100ms（lib.rs:324）—— **太小**
2. `trim_segment_head_tail` 用 20ms RMS window 找 head 第一个 above-threshold 位置（lib.rs:7326-7333），然后保留 `pre_roll_ms` 余量。**默认 100ms 不够给「自然呼吸」感**
3. `gate_segment_head_tail` 之后又把残留 below-threshold 部分置零 —— 留下来的 100ms 还可能全是 silence-detected 但低于阈值的环境噪声，gate 把它「清干净」后听感更突兀

**整改方案 M2**：
- **A（推荐，1 行改）**：`default_pre_roll_ms()` 从 100 提到 **250-300**（lib.rs:324）。让 segment 头部至少 0.25 秒「呼吸感」。
- **B（彻底）**：在 `cut_audio_file_dialect_impl` 里**完全跳过 `trim_segment_head_tail`**（删除 lib.rs:3409-3419）。让 `silencedetect` + `build_segment_ranges` + `pre_roll/post_roll` 完全决定边界，不再做二次 trim。`gate_segment_head_tail` 也可以同时删（依赖 M1 已修 click）。
- **C**：保留 trim 但只作为「兜底」——如果 silencedetect 找到的 silence_end 距离实际语音超过 `pre_roll_ms * 3`，才动；否则不动。

**推荐 A + C 组合**：A 立竿见影，C 让 trim 不再过度激进。

### 7.3 问题 3：「切得太碎了」

**用户描述**：切片数量过多/太短。

**用户约束（2026-05-14 补充，已修正）**：
- **`max_segment_ms` 是用户配置项**（`CutConfig.max_segment_ms`，默认 0 = 无上限）。用户当前实际配的是 30000（30s 典型值），但**不是硬编码**。所有合并 / 切分逻辑要**读 `config.max_segment_ms`**，并把 0 当作无上限处理（与 `build_segment_ranges` 现有语义保持一致）。**绝对不要硬编码 30000**——破坏其他配置的用户。
- **Mode 1 音频特征**：中间会出现「较长的静音段」（自由对话场景的自然停顿、思考间隙）；Mode 2（普通话朗读）的音频没有这种特征
- 所以**不能直接照搬 Mode 2 的「LLM 选切点 + 6-90s 范围」逻辑** —— Mode 2 的算法基于「音频里没有长 silence 浪费空间」的假设

**根因**：
- `min_silence_ms` 默认 400ms（lib.rs:322）——0.4 秒呼吸停顿就触发切
- `min_segment_ms` 默认 300ms（lib.rs:323）——0.3 秒短语音都单独成段
- `build_segment_ranges` (lib.rs:6902) **没有「短段合并到相邻段」的后处理逻辑**
- Mode 1 录音里的「长静音段」单独占据 silencedetect 区间被跳过，但**长静音前后的短 voice 段就这样单独成段**，没有跨长静音合并机制

**整改方案 M3-revised**：

#### M3.1 默认参数调大（简单）
`default_min_silence_ms` 400 → **800**（lib.rs 函数名待确认，搜 `min_silence_ms` 找 default）
`default_min_segment_ms` 300 → **2000**
**不改** `default_max_segment_ms`（保持 0 = 无上限的现有语义；用户自己在 UI 上配实际想要的值）

效果：单独碎段会少一半。但「长静音前后的短段」问题不解决——长静音永远算切点。

#### M3.2 短段合并后处理（关键，**Mode-1 特有逻辑**）
`build_segment_ranges` 末尾加 post-processing pass。**关键算法**：

```text
# 用户配置上限。0 = 无上限（沿用 build_segment_ranges 现有语义）
max_total_ms = if config.max_segment_ms > 0 { config.max_segment_ms } else { u64::MAX }

扫 ranges 数组：
对每个 range[i]：
    if duration(range[i]) < min_segment_ms * 1.5:
        # 短段。尝试合并到相邻段
        merge_target = 选择 ranges[i-1] 和 ranges[i+1] 中较短的一个
        if merge_target.duration + range[i].duration + gap_silence <= max_total_ms:
            # 注意 gap_silence！合并跨长静音，总时长把中间静音也算上
            合并 + 删除 range[i]
        else:
            # 短段无法合并到任一相邻段（受用户配置 max_segment_ms 约束）→ 保留独立
            保留
```

**关键设计点**：
- 合并时**算上中间的长 silence 时长**（gap_silence = range[i].start - range[i-1].end）
- 上限读 `config.max_segment_ms`，**不要硬编码 30000**。用户配置 0（无上限）时永远能合并
- **不压缩 / 不删除中间的 silence**——保留为 segment 内部时长。这跟 Mode 2 的「连续语音段」不一样，Mode 1 segment 内允许有长静音

代码位置：lib.rs:6902-7000 `build_segment_ranges` 末尾加 post-processing pass。新增 helper：
- `fn merge_short_ranges(ranges: Vec<(f64, f64)>, min_dur: f64, max_dur: f64) -> Vec<(f64, f64)>`
- 单测：
  - 短段在中间 → 合并到较短邻段
  - 短段在头部 → 合并到 ranges[1]（如果 ranges[1] 短）
  - 短段在尾部 → 合并到 ranges[-2]
  - 合并会超 30s → 保留独立
  - 没有相邻段 → 保留独立

#### M3.3 段内长静音的处理（可选，等 M3.1+3.2 落地后看效果）

如果 M3.2 合并后用户反馈「段内 silence 太长听感不连贯」，再加一步：
- 用 ffmpeg `silenceremove` filter（threshold = silence_db，period = e.g. 1s）压缩段内 > 1s 的静音
- 或者：仍然保留 silence 但做 `arnndn` 降噪
- 让用户在 ConfigBand 配置「是否压缩段内静音」（CompressInternalSilence bool）

**默认建议保留**（不压缩）—— 真实自由对话本来就有停顿，强行压缩听起来不自然。

#### M3.4 UX 暴露参数（P2 polish）
把 `min_silence_ms` / `min_segment_ms` / `max_segment_ms` 在 ConfigBand UI 上暴露——当前藏在 JSON 里，用户不会调。这是「让用户可以根据录音类型自调」的兜底方案。

### 7.3a 借鉴 Mode 2 LLM 辅助的可行性（**结论：暂不引入**）

用户在 session 中提过「能不能借鉴 Mode 2 中 AI 辅助切割的逻辑」。回答：**Mode 1 暂不直接借鉴**。原因：

1. **Mode 2 算法基于的假设 Mode 1 不满足**：
   - Mode 2 滑窗 + LLM 选切点的逻辑（lib.rs:2658+）假设「窗口内音频是连续语音」——LLM 看 Whisper 转写的 segment 列表选一个 end_ms 作切点
   - Mode 1 音频中间有长静音段，silencedetect 已经处理了这种情况；用 LLM 介入反而把简单问题复杂化

2. **用户配置的 max_segment_ms（通常 30s）不能突破**：
   - Mode 2 默认 max=90s，LLM 的 prompt 里 sweet_lo/sweet_hi 也是按 90s 计算的
   - 要让 LLM 遵守用户配置的 30s 上限就要重写 prompt + 重新调试 LLM 行为
   - 不如纯启发式合并直接

3. **方言场景 Whisper 准确率低**（HANDOFF §8 #1 + §6.12 缓解过 prompt）：
   - 用 LLM 看「质量差的转写」做合并决策，不如「看时长 + silence 间隔」启发式可靠
   - Mode 1 主要服务方言录音，不是 Mode 2 的普通话场景

4. **Mode 1 的设计哲学是「快速、便宜、无外部依赖」**（HANDOFF §6.4 + §6.9）：
   - 引入 Whisper 调用 + Ollama 调用会破坏 Mode 1 的轻量定位
   - 用户 Mode 1 流程当前不依赖 Whisper / Ollama 池

**未来如果 M3.2 启发式合并仍然不够好（next-next session 才考虑）**：
- 方案 D：silence-cut → Whisper 转写每段 → **用标点信号**（不用 LLM）决定相邻段合并
  - 短段往前找：上段 transcript 结尾没标点 → 合并；有句末标点（。？！）→ 保留独立
  - 标点比「LLM 理解方言」对错转写更鲁棒（Whisper 加错字但加对标点的概率高）
  - 仍受 `config.max_segment_ms` 约束（用户配置值）
- 这是「Mode 2 思想 + Mode 1 约束」的混合方案，不是直接借鉴 Mode 2 代码

**真正想要 LLM 智能 + 用户配置上限的用户 → 长期方案**：
- 给 Mode 2 加个「方言模式」开关，让 max_segment_s 可配置到 30s（或用户想要的任何值）
- 重写 LLM prompt 里的 sweet_lo / sweet_hi 计算逻辑用新上限
- 这是 P3 长远规划，不在本次 Mode 1 修复范围
