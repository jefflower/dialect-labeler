## 7. Mode 1 切割质量问题（用户截图 + 整改计划，2026-05-14 补）

用户在 session 末尾发了 3 张截图 + 3 段描述指出 Mode 1（dialect 切割）有三个串联的质量问题。**没在代码层面改**，只做了代码定位 + 根因分析 + 整改方案。下个 session 第一优先级。

### 7.1 问题 1：「悬崖一样的切割线」（频谱紫色垂直线 + 听觉 click）

**用户描述**：截图上波形里有「悬崖」般的不连续，频谱图上对应一条紫色窄带（所有频率同时被激发）。第二张截图是「正常应该这样」——平滑衰减。

**直接根因**：`src-tauri/src/lib.rs::gate_segment_head_tail` (lib.rs:7395-7514)
- 该函数把头尾 below-threshold 的 sample 逐字节置零
- **置零位置和首个非零样本之间是阶跃跳变** → click 噪声
- 代码片段：
  ```rust
  // lib.rs:7498-7511
  let head_bytes = head * frame_size;
  if head_bytes > 0 {
      for b in &mut bytes[data_start..data_start + head_bytes] {
          *b = 0;  // ← 一刀切到 0，没有 ramp
      }
  }
  ```

**间接根因**：`write_pcm_wav_segment` (lib.rs:7671) 也是 ffmpeg `-ss / -t` 硬切，**没有 fade in / fade out**。

**整改方案 M1（高优先级）**：
- **A（推荐，最小改动）**：在 `gate_segment_head_tail` 置零边界加 **3-5ms 线性 ramp**（head 从 0 渐升到原样本，tail 从原样本渐降到 0）。code 位置 lib.rs:7498-7511，加一个 ramp_frames = sample_rate * 5 / 1000 的过渡区间。
- **B（更干净）**：彻底删 `gate_segment_head_tail`，把 fade 直接合入 `trim_segment_head_tail` 输出。
- **测试**：合成一段头部 -20dB 噪声 + 中段 -3dB 信号的 WAV，gate 后用 FFT 验证没有不该有的全频段噪声。

### 7.2 问题 2：「前面几乎没有静音段了」

**用户描述**：截图 3 显示一段音频开头几乎没有 silence padding，立刻进入声音。

**根因链**：
1. `pre_roll_ms` 默认 100ms（lib.rs:324）—— **太小**
2. `trim_segment_head_tail` 用 20ms RMS window 找 head 第一个 above-threshold 位置（lib.rs:7326-7333），然后保留 `pre_roll_ms` 余量。**默认 100ms 不够给「自然呼吸」感**
3. `gate_segment_head_tail` 之后又把残留 below-threshold 部分置零 —— 留下来的 100ms 还可能全是 silence-detected 但低于阈值的环境噪声，gate 把它「清干净」后听感更突兀

**整改方案 M2**：
- **A（推荐，1 行改）**：`default_pre_roll_ms()` 从 100 提到 **250-300**（lib.rs:324）。让 segment 头部至少 0.25 秒「呼吸感」。
- **B（彻底）**：在 `cut_audio_file_dialect_impl` 里**完全跳过 `trim_segment_head_tail`**（删除 lib.rs:3409-3419）。让 `silencedetect` + `build_segment_ranges` + `pre_roll/post_roll` 完全决定边界，不再做二次 trim。`gate_segment_head_tail` 也可以同时删（依赖 M1 已修 click）。
- **C**：保留 trim 但只作为「兜底」——如果 silencedetect 找到的 silence_end 距离实际语音超过 `pre_roll_ms * 3`，才动；否则不动。

**推荐 A + C 组合**：A 立竿见影，C 让 trim 不再过度激进。

### 7.3 问题 3：「切得太碎了」

**用户描述**：切片数量过多/太短。

**根因**：默认参数对自由对话过度敏感
- `min_silence_ms` 默认 400ms（lib.rs:322）——0.4 秒呼吸停顿就触发切
- `min_segment_ms` 默认 300ms（lib.rs:323）——0.3 秒短语音都单独成段
- `build_segment_ranges` (lib.rs:6902) 没有「短段合并到相邻段」的后处理逻辑

**整改方案 M3**：
- **A（推荐，2 行改）**：默认值改成 `min_silence_ms=800` / `min_segment_ms=2000`（lib.rs:322-323）。这是社区做 ASR 数据集的常用基准：呼吸停顿 >0.8s 才算句间停顿，最短 2s 才单独成段。
- **B（更稳）**：A + 增加**短段合并**后处理——`build_segment_ranges` 末尾扫一遍 ranges，把短于 `min_segment_ms * 1.5` 的段合并到相邻较短段。
- **C（UX）**：把 `min_silence_ms` / `min_segment_ms` 在 ConfigBand UI 上暴露，让用户根据录音类型自调（剧本对白用小值、自由对话用大值）。当前是「藏在配置 JSON 里」，普通用户不知道。

**推荐先 A**，5 分钟改完让用户感受效果；如果还碎再做 B；C 是 UX polish 留到 P1。

### 7.4 集成测试建议

每个修复都加单元测试，并跑一次真实端到端：
1. 用一段已知有 click 问题的真实长沙话录音
2. 跑 Mode 1 切割
3. 用 Audacity 或类似工具肉眼检查：

   - 切片数量合理，无 <2s 的孤立短段（M3）
4. 把修复前后的截图存到 `docs/screenshots/mode1-fix-2026-05-XX/` 留档
